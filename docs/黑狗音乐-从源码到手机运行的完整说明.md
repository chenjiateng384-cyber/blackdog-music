历史讲解基线：0.4.0+5。当前源码为 0.4.6+12，ARM64 拆分测试包实际编号 2012；构建、签名和交付状态以[陌生用户走查](FIRST_USER_WALKTHROUGH.md)与[发布指南](RELEASING.md)为准，下文历史 APK 名称不是当前下载链接。

更新日期：2026年10月11日

适合读者：第一次接触软件开发，希望真正理解项目里每类文件做什么的人。

- 为什么电脑里的文件可以变成手机里能运行的 App。
- 哪些文件可以重新生成，哪些数据必须备份。
- 出现界面、扫描、播放或数据问题时，应先检查哪一层。

## 快速认识整个系统

| 内容 | 实际位置 | 作用 | 丢失后的影响 |
| --- | --- | --- | --- |
| 项目源码 | 电脑项目目录 | 定义界面、扫描、播放和数据逻辑 | 无法继续维护和重新构建 |
| Git 历史 | 项目中的 `.git/` | 记录版本并提供回退能力 | 修改出错后难以恢复 |
| APK | `dist/` | 可直接安装到 Android 手机 | 可以重新构建，通常不影响源码 |
| App 数据库 | 手机 App 私有目录 | 保存喜欢、歌单、历史和人工修正 | 卸载或清除数据后会丢失 |
| 原始音乐 | 手机音乐目录 | 用户实际拥有的音频与 LRC | App 无法播放对应内容 |
| 构建工具 | `.tooling/` | 把源码编译成 APK | 可以重新安装，不属于软件业务源码 |

## 1. 先用一句话理解整个项目

电脑上的项目文件是“设计图、原材料和生产工具”，APK 是“生产完成并封装好的产品”，手机安装则是“把产品放进手机并登记到 Android 系统”。

手机运行 App 时，不会不断回电脑读取 `lib`、`android` 或数据库代码。USB 拔掉以后仍然能运行，是因为需要执行的程序已经被编译并安装进手机。

可以把完整过程理解成：

```text
电脑上的源码
    ↓ Flutter、Dart、Kotlin、Gradle 编译
Android 可执行代码 + 图片 + 图标 + 配置 + 依赖
    ↓ 打包和签名
黑狗音乐 APK
    ↓ USB / adb 安装
Android 把 APK 安装到手机应用区
    ↓ 用户打开 App
App 扫描手机音乐目录、读取手机数据库并播放音乐
```

## 2. 电脑上到底放了什么

项目根目录是你克隆或保存源码的位置，例如：

```text
你的工作目录/个人音乐库项目
```

它不是一份单独的“软件文件”，而是一个完整的软件工程。

### 2.1 `lib/`：软件的大脑和绝大部分界面

这里是 Flutter 的 Dart 源码，也是日常功能修改最多的地方。

#### `lib/main.dart`

这是 Flutter 程序的主入口。

手机点击黑狗音乐图标后，Android 创建 Flutter 运行环境，随后进入这里的 `main()`：

1. 初始化 Flutter。
2. 初始化后台音频服务。
3. 指定通知栏音乐频道和通知图标。
4. 创建黑狗音乐 App。
5. 加载首页、音乐库、歌单、我的和播放器。

这里还管理了主导航、搜索页开关、Mini Player、返回键和 App 进入后台时保存播放状态。

#### `lib/controllers/`

目前主要是 `app_controller.dart`。

可以把 Controller 理解为“总调度员”。界面本身只负责展示；真正需要扫描、查询、播放、收藏、搜索或创建歌单时，界面会把请求交给 Controller。

Controller 负责连接：

- 数据库。
- 音乐扫描器。
- 播放器。
- 歌词服务。
- 搜索。
- 喜欢和歌单。
- 随心听与智能播放。
- 播放历史。
- 备份恢复。

它也是当前较大的文件之一，后续应谨慎拆分，但不应该为了好看而一次重写。

#### `lib/models/`

这里定义“数据长什么样”。

例如：

- Track：用户看到的一首逻辑歌曲。
- MediaFile：手机上的一个真实音频文件。
- Artist：歌手。
- Album：专辑。
- Playlist：歌单。
- Lyrics：歌词引用和时间轴。
- Playback：播放模式、队列和来源。

Model 本身通常不负责画界面，也不负责直接读取文件。它像表格的列定义，规定各部分怎样交换数据。

#### `lib/data/`

这里是 Repository，也就是“数据库办事窗口”。

例如：

- `library_repository.dart`：查询歌曲、歌手、专辑和文件夹。
- `playlist_repository.dart`：创建歌单、添加歌曲、排序和删除。
- `lyrics_repository.dart`：查询歌曲关联的歌词。
- `playback_history_repository.dart`：保存播放事件和统计。
- `scan_repository.dart`：保存扫描结果。
- `v4_schema.dart`：定义 SQLite 数据表和数据库版本。

这样做的原因是避免页面到处直接写 SQL。以后修改数据库查询时，可以集中在 Repository 层处理。

#### `lib/services/`

这里负责持续运行或需要复杂流程的业务。

重要例子：

- `music_audio_handler.dart`：后台播放、通知栏、锁屏媒体控制。
- `playback_queue.dart`：播放队列、上一首、下一首、插播和顺序。
- `library_scan_service.dart`：协调一次完整扫描。
- `metadata_inference.dart`：根据目录和文件名保守推断歌手、专辑和曲序。
- `metadata_resolver.dart`：按优先级组合用户修改、文件标签和推断结果。
- `lrc_parser.dart`：把 LRC 文本解析成带时间的歌词行。
- `lyrics_service.dart`：查找并提供当前歌曲歌词。
- `home_quick_start_radio.dart`：随心听候选与动态队列。
- `home_smart_play_pool.dart`：每日智能播放池。
- `harmony_backup_service.dart`：导出和恢复 `.harmonybackup`。
- `library_database.dart`：打开 SQLite 数据库并执行安全升级。

#### `lib/ui/`

这里决定用户实际看到什么。

包括：

- 首页。
- 音乐库。
- 歌单。
- 搜索。
- 我的。
- 完整播放页。
- 歌手和专辑详情页。
- 真实封面组件。
- Mini Player。
- 颜色、字号、间距和圆角规范。

当你说“封面往上移”“歌名间距调整”“播放按钮不好看”时，主要修改的就是这里。

#### `lib/utils/`

放小型公共工具，例如中文拼音排序。它们不属于某一个页面，但多个模块都需要使用。

### 2.2 `android/`：Flutter 与 Android 手机之间的桥

Flutter 能处理大多数界面和业务，但读取 Android 文件、请求权限、后台媒体服务等功能需要 Android 原生配置或 Kotlin 代码。

#### `AndroidManifest.xml`

这是 Android 的应用登记表，告诉系统：

- App 名称是黑狗音乐。
- 启动页面是哪一个。
- 需要读取音频、前台播放和唤醒锁等权限。
- 存在后台音乐服务。
- 存在耳机和媒体按钮接收器。
- App 图标使用哪个资源。

Android 安装 APK 时会读取这份配置。

#### `MainActivity.kt`

这是 Android 启动 Flutter 的原生入口，也是 Dart 与 Android 沟通的一座桥。

它通过 MethodChannel 接收 Flutter 请求，例如：

- 扫描系统媒体。
- 读取内嵌封面。
- 调用 Android 文件接口。
- 处理目录授权。
- 处理备份文件的选择和保存。

#### 其他 Kotlin 文件

- `SafMusicScanner.kt`：递归读取用户授权的真实音乐目录。
- `AudioTagReader.kt`：读取 FLAC、MP3、WAV 等标签和封面。
- `ContentHashReader.kt`：计算文件 Hash，识别重复或移动后的文件。
- `ScanRootBridge.kt`：让用户选择音乐根目录并保存长期访问权限。
- `BackupBridge.kt`：通过 Android 文件选择器导出或导入备份。
- `TextDocumentReader.kt`：读取 LRC 等文本文件。
- `MediaStoreLookup.kt`：查询 Android MediaStore 媒体信息。

#### `build.gradle`

它是 Android 的“生产说明书”，规定：

- 包名是 `com.chenjiateng.my_music_library`。
- 使用哪个 Android SDK 和 NDK。
- Kotlin/Java 编译标准。
- Flutter 源码在哪里。
- 生成 Debug 还是 Release APK。
- APK 使用什么签名。

当前 Release 使用的是 Debug 签名配置。个人手机覆盖安装可以使用，但如果未来正式上架应用商店，应创建并妥善保存独立 Release 签名密钥。

### 2.3 `test/`：自动检查程序

这里不是 App 功能，而是用来检查 App 功能的代码。

测试覆盖：

- 数据库表和迁移。
- 搜索结果。
- 歌手、专辑和文件夹聚合。
- 播放队列。
- 播放历史。
- 歌单。
- 歌词解析。
- 随心听和智能播放。
- UI 关键状态。
- 真实目录验收。

运行测试不会让软件自动变好，但能提前发现“修改 A 时把 B 弄坏”的问题。

### 2.4 `docs/`：产品规则、报告和使用说明

这里保存：

- 产品体验检查报告。
- 日常使用手册。
- UI 阶段报告。
- 设计样稿。
- 增强 LRC 说明。
- 项目复盘。
- 当前这份源码到手机运行说明。

文档不会被手机直接执行，但它们能防止长项目在换模型、换 Agent 或几个月后忘记原本规则。

### 2.5 `tools/`：特殊离线工具源码

目前主要是歌词对齐工具。

它与手机 App 分开运行，用于在电脑上处理音频和歌词，生成带更细时间信息的歌词。它不是黑狗音乐每次启动都要运行的部分。

### 2.6 `shaders/`：少量图形效果

Shader 是给图形处理器运行的小程序，用于水波、拉伸等视觉效果。它们会被一起打进 APK。

### 2.7 `pubspec.yaml`：Flutter 项目的总清单

它记录：

- 项目内部名称。
- 当前版本 `0.4.0+5`。
- 使用哪些第三方能力。
- 是否包含 Material 图标。
- 要打包哪些 Shader。

其中重要依赖：

- `just_audio`：实际音频播放。
- `audio_service`：后台播放、通知栏和锁屏控制。
- `sqflite`：手机 SQLite 数据库。
- `file_picker`：选择文件或备份。
- `permission_handler`：Android 权限。
- `crypto`：SHA-256 等校验。
- `pinyin`：中文拼音排序。
- `shared_preferences`：少量设置和轻量状态。

### 2.8 `pubspec.lock`：依赖的精确版本

`pubspec.yaml` 表示允许使用什么范围，`pubspec.lock` 记录这次实际用了哪个精确版本。保留它能减少“今天和下次构建结果不一样”的风险。

### 2.9 `.tooling/`：本机生产工具

这里不是 App 源码，而是为了在这台电脑上能够编译而保存的工具：

- Flutter SDK。
- JDK。
- Gradle 缓存。
- Flutter/Dart 依赖缓存。
- 歌词对齐运行环境和模型。
- 少量设备数据备份。

它占用空间大，但不会整个装进手机。删除后源代码还在，只是下一次编译可能需要重新下载工具和依赖。

### 2.10 `.git/`：项目的时间机器

Git 保存代码版本、分支和提交历史。

它可以回答：

- 某次修改前代码是什么样。
- 哪个版本引入了 Bug。
- 哪些文件被修改。
- 如何回退到稳定版本。

`.git` 不会打进 APK，也不在手机运行。它只服务于开发和恢复。

### 2.11 `dist/`：最终安装包

当前保留：

```text
dist/黑狗音乐-v0.4.0-arm64-release.apk
```

这才是可以直接传到 Android 手机并安装的文件。

## 3. 源码是怎样变成 APK 的

执行 Flutter 构建时，大致发生以下事情。

### 第一步：读取项目配置

Flutter 读取 `pubspec.yaml`，Gradle 读取 Android 配置，确认依赖、版本、包名和资源。

### 第二步：编译 Dart

Release 构建会把 Dart 业务代码编译为适合手机处理器执行的机器代码，而不是把所有 `.dart` 文件原样交给手机解释。

### 第三步：编译 Kotlin 和 Android 代码

Android 的扫描器、Metadata 阅读器、文件桥接和启动入口被编译成 Android 可以执行的字节码。

### 第四步：合并资源

图标、通知栏图标、Android Manifest、字体、Shader 等资源被整理并编号。

此前“通知图标在 Release 闪退”的根因，就是资源压缩时认为一个只通过字符串引用的图标没有被使用。后来增加了保留规则，明确告诉打包器不能删除该图标。

### 第五步：打包依赖

Flutter 引擎和需要的插件会随 APK 一起打包。正因为 Flutter 引擎也包含在里面，APK 才会有几十 MB。

### 第六步：生成并签名 APK

Android 不允许安装没有签名的 App。签名相当于开发者印章：

- 相同包名 + 相同签名：可以覆盖升级，并保留数据。
- 相同包名 + 不同签名：Android 会拒绝覆盖安装。
- 卸载后再安装：签名可以相同，但原私有数据通常已经被系统删除。

## 4. APK 是怎样进入手机的

手机打开 USB 调试并授权电脑以后，Android Debug Bridge（ADB，安卓调试桥）可以与手机通信。

覆盖安装使用的概念类似：

```text
adb install -r 黑狗音乐-v0.4.0-arm64-release.apk
```

其中 `-r` 表示替换现有程序但尽量保留 App 私有数据。

安装时：

1. 电脑通过 USB 把 APK 发送给手机。
2. Android 包管理器验证 APK 签名。
3. 检查包名和版本。
4. 把 App 文件安装到 Android 管理的应用目录。
5. 在桌面创建“黑狗音乐”入口。
6. 保留或创建对应的私有数据目录。

安装完成后，电脑断开不会影响运行，因为 APK 已经复制到了手机。

## 5. 为什么电脑上没有音乐，手机仍然能播放

因为 APK 只包含播放器程序，不包含你的几百首音乐。

首次选择“音乐文件”根目录时，App 使用 Android SAF 获得一个 Tree URI。可以把它理解为 Android 给黑狗音乐的一张长期通行证：允许它读取这个目录和子目录，但不等于把音乐复制进 App。

扫描后数据库保存的是：

- 稳定 Track ID。
- Content URI。
- 相对目录和文件名。
- Metadata。
- 文件大小、修改时间和 Hash。
- 封面、歌词和用户偏好关系。

播放时，播放器根据 Content URI 向 Android 请求读取原音频，然后把音频数据交给 `just_audio` 解码播放。

所以：

- 删除 APK 不会删除原始音乐。
- 删除原始音乐后，App 会失去对应可播放文件。
- 把音乐移动后重新扫描，系统会尝试凭身份信息和 Hash 重新关联 Track。

## 6. 手机上的数据分别放在哪里

### 原始音乐

仍在用户自己选择的音乐根目录里。黑狗音乐默认只读，不主动改名、移动或删除。

### App 数据库

数据库文件名是：

```text
my_music_library.db
```

Android 会把它放在黑狗音乐的私有数据库目录。普通文件管理器通常不能直接看到。

数据库保存：

- Track 和 MediaFile。
- 歌手、专辑和目录关系。
- 喜欢。
- 歌单及顺序。
- 播放历史和统计。
- 歌词引用。
- Metadata 和人工修改。
- 推荐排除状态。
- 扫描记录。

### SharedPreferences

适合保存少量轻量设置，例如某些页面状态、当天智能播放池或备份提醒时间。它不适合存几百首完整歌曲记录。

### App 缓存和私有资源

可能包含封面缓存、人工封面和临时文件。可重新生成的缓存与不可重新生成的用户资源必须区别对待。

### `.harmonybackup`

这是用户主动导出的外部备份。只有保存到 App 外部目录、电脑或网盘，卸载后才不会一起消失。

## 7. 打开 App 后内部发生了什么

```text
点击桌面图标
    ↓
Android 根据 Manifest 启动 MainActivity
    ↓
MainActivity 创建 FlutterEngine
    ↓
进入 lib/main.dart 的 main()
    ↓
初始化 AudioService 后台播放服务
    ↓
创建 AppController
    ↓
打开 SQLite 数据库并检查迁移
    ↓
查询音乐库、喜欢、歌单、播放状态
    ↓
Flutter 根据数据绘制首页和 Mini Player
```

页面不是一张固定图片。Flutter 每次根据当前状态绘制组件：歌曲变化、喜欢状态变化或播放位置变化时，对应区域会重新显示。

## 8. 扫描一次音乐时发生了什么

```text
用户选择音乐根目录
    ↓
Android 保存长期目录授权
    ↓
SafMusicScanner 递归发现音频、LRC、图片
    ↓
AudioTagReader 读取真实标签和内嵌封面
    ↓
Dart 接收原始扫描结果
    ↓
Metadata Resolver 按优先级整理显示信息
    ↓
File Identity 判断新文件、移动文件和重复文件
    ↓
Repository 分批写入 SQLite
    ↓
Controller 重新查询并通知 UI
    ↓
音乐库页面出现新歌曲
```

Metadata 优先级大致是：

```text
用户人工修改
> 文件真实标签
> 目录推断
> 文件名推断
> 未知
```

## 9. 点击一首歌时发生了什么

```text
用户点击歌曲
    ↓
页面把 Track 和当前上下文交给 AppController
    ↓
Controller 创建或切换播放队列
    ↓
Track 选择 Preferred MediaFile
    ↓
MusicAudioHandler 把 Content URI 交给 just_audio
    ↓
音频开始解码和播放
    ↓
AudioService 更新通知栏、锁屏和耳机控制
    ↓
播放状态流通知 Mini Player 和完整播放页
    ↓
PlaybackHistoryService 保存播放事件和时长
```

Mini Player、完整播放页和通知栏不是三个播放器，它们只是控制同一个后台播放器的三个界面。

## 10. 我在开发过程中实际做了什么

作为开发 Agent，工作并不是简单“生成一个软件文件”，而是循环进行以下动作：

1. 阅读现有源码和项目规则。
2. 根据需求定位应该修改的层级。
3. 修改 Dart、Kotlin、Android 配置、测试或文档。
4. 运行静态检查，找语法、类型和规范问题。
5. 运行自动测试，检查数据库、搜索、队列、歌词等逻辑。
6. 使用 Gradle 和 Flutter 构建 APK。
7. 通过 ADB 把 APK 覆盖安装到一加13。
8. 读取手机日志，查找崩溃、ANR 和异常。
9. 检查手机数据库快照、媒体会话和通知栏状态。
10. 获取真机截图或界面结构，对照设计。
11. 修复问题后重复检查。

代码修改发生在电脑项目里；测试、构建和安装命令只是利用这些文件产生结果。只有重新构建并安装后，手机才会得到最新代码。

## 11. 电脑文件与手机 App 之间哪些操作互不影响

### 删除电脑上的 `build/`

不会删除手机 App。它只是上一次编译的临时产物，下次可以重新生成。

### 删除电脑上的 APK

不会卸载手机里已经安装的 App，但以后失去这份安装包。

### 删除电脑源码

不会立即让手机 App 消失，但以后无法继续修复或重新构建，因此源码必须保护。

### 在电脑修改 Dart 文件

不会自动改变手机。必须重新构建并安装。

### 卸载手机 App

不会删除用户音乐目录，但通常会删除 App 私有数据库、喜欢、歌单、播放历史和内部资源。

### 覆盖安装同签名 APK

通常保留 App 私有数据，因此日常测试优先使用覆盖安装。

## 12. Debug 与 Release 有什么区别

### Debug

- 方便调试。
- 带更多诊断能力。
- 体积较大。
- 性能不代表最终产品。
- 发生 Flutter 错误时可能显示红屏。

### Release

- 编译和优化更充分。
- 更接近日常使用性能。
- 关闭大部分调试信息。
- 适合最终真机验收和长期使用。

因此，讨论卡顿和真实体验时，应以 Release 版本为主，不能只根据 Debug 版下结论。

## 13. 为什么一个小修改也可能产生 Bug

音乐 App 的状态彼此相连。例如播放页按钮变化可能涉及：

- Flutter UI。
- Controller 当前歌曲状态。
- 播放队列。
- 后台 AudioService。
- Android 通知栏。
- 播放历史。
- App 前后台生命周期。

如果只看页面而没有测试后台，或者只测试逻辑没有检查真机，就可能出现“页面正常但通知崩溃”或“能播放但 Mini Player 不更新”。

这也是为什么项目需要自动测试、真机测试和 Git 回退点，而不能只靠一次编译成功。

## 14. 你以后最值得认识的几个文件

不需要一次学会全部代码。先认识这些即可：

1. `README.md`：项目是什么。
2. `pubspec.yaml`：版本和依赖。
3. `lib/main.dart`：App 从哪里启动。
4. `lib/controllers/app_controller.dart`：主要业务如何协调。
5. `lib/ui/v4_pages.dart`：主要页面。
6. `lib/ui/v4_player_page.dart`：播放页面。
7. `lib/services/music_audio_handler.dart`：后台播放器。
8. `lib/services/library_scan_service.dart`：扫描流程。
9. `lib/data/v4_schema.dart`：数据库结构。
10. `android/app/src/main/AndroidManifest.xml`：Android 权限和组件。
11. `test/`：怎样证明功能没有坏。
12. `dist/黑狗音乐-v0.4.0-arm64-release.apk`：当前面向一加13的可安装产品。

## 15. 目前项目需要注意的工程事实

### 版本、提交和 APK 必须保持一致

本次开始把当前功能收口为 0.4.0 稳定检查点。以后每次正式交付都应让版本号、Git 提交、测试结果和 APK 一一对应。这样手机出现问题时，才能准确知道它来自哪一版，也能回退到上一个稳定版本。

### Release 仍使用 Debug 签名

个人测试和同签名覆盖安装没有问题。但如果未来更换电脑、丢失签名文件或希望上架，需要正式管理 Release Key。否则 Android 会把不同签名视为不同开发者，无法直接覆盖原 App。

当前阶段不能直接更换签名，因为 Android 会拒绝覆盖安装，通常需要先卸载旧 App，可能造成用户数据丢失。现阶段继续使用原签名保证安全覆盖；未来准备正式发布时，再单独制定签名迁移方案。

### OneDrive 不能代替 Git 和 App 备份

OneDrive 主要保护电脑文件，Git 负责记录源码版本，`.harmonybackup` 负责保护手机中的收藏、歌单和播放历史。三者解决的问题不同，不能互相替代。

## 16. 每次安全发布的标准流程

```text
确认需求范围
    ↓
只修改必要文件
    ↓
静态检查和自动测试
    ↓
构建 Release APK
    ↓
建立 Git 稳定提交与版本标签
    ↓
使用同签名覆盖安装
    ↓
在一加13验证启动、扫描、播放、返回和后台控制
```

不要用“成功编译”代替验收。真正完成至少要同时满足：代码检查通过、测试通过、APK 构建成功、真机关键流程正常。

## 17. 出现问题时怎样判断是哪一层

| 现象 | 优先检查 | 常见原因 |
| --- | --- | --- |
| 页面错位、按钮不见 | `lib/ui/`、主题和组件 | 布局约束、状态未刷新或图标资源问题 |
| 扫描不到歌曲 | ScanRoot、SAF 权限、扫描服务 | 目录授权失效、格式未识别或扫描中断 |
| 歌名或封面错误 | Metadata、Artwork 查询与缓存 | 标签缺失、优先级错误或缓存文件失效 |
| 点击歌曲不播放 | Track、首选 MediaFile、播放器 | 文件不可访问、队列上下文错误或音频初始化失败 |
| 后台或锁屏控制异常 | AudioService、通知和 Android 配置 | 媒体会话状态不同步或系统权限问题 |
| 喜欢、歌单或历史不见 | SQLite 数据库与备份 | 清除数据、卸载或恢复流程未完成 |
| 只有 Debug 卡顿 | Release 真机重新验证 | Debug 诊断开销，不代表正式包性能 |

排查时先复现，再看日志，最后只改与根因有关的文件。不要因为一个按钮有问题就重写整个页面，也不要因为一次扫描异常就删除数据库。

## 18. 最后用“餐厅”再比喻一次

- `lib/`：菜谱和前厅工作方式。
- `android/`：厨房设备与本地法规许可。
- `pubspec.yaml`：采购清单。
- `.tooling/`：炉灶、刀具和生产设备。
- `test/`：食品检查流程。
- `docs/`：经营手册和装修图。
- Git：监控录像和历史档案。
- APK：打包完成、可以带走的成品。
- ADB 安装：把成品送进手机并登记。
- SQLite：这位用户自己的会员档案和消费记录。
- 音乐目录：用户自己拥有的食材仓库，App 只读取，不占为己有。

理解这张关系图以后，你不需要会写全部代码，也能知道一次修改会影响哪里、哪些文件绝对不能乱删、为什么安装后可以离开电脑运行，以及为什么数据备份和版本签名如此重要。
