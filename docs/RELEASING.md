# 第一次把黑狗音乐发布到 GitHub

你不需要把电脑里的整个项目文件夹拖上去。GitHub 放可复现的源码；Releases 放经过验收的安装包；手机音乐、收藏数据库和私钥都不公开。

平台、命名、附件与本次实际检查结果见[发布前最终核对](RELEASE_READINESS.md)。当前只准备 Android，不能把 Flutter 源码存在理解成已有 iPhone 版本。

## 已确定的选择

- 先交付可保留现有数据的本地测试版，再准备专属签名的正式公开 APK。
- 不为换签名卸载 App，不清空数据，不把唯一真机当破坏性试验环境。
- 2026-11-03 已在所有者核验账号创建私有仓库 `chenjiateng384-cyber/blackdog-music`，准备提交审查过的干净副本；尚未公开或发布 Release。源码审阅、线上检查与正式签名仍按各自关卡验收。

## 1. 先验收测试版

运行 `tool.ps1 build-local-test`，得到 ARM64 release 性能测试 APK。它明确使用本机调试证书，仅用于原有手机的兼容测试，不应作为“正式安全签名版”公开推广。

安装前用 Android SDK 的 `apksigner verify --print-certs` 比较新包与手机已安装包的证书 SHA-256。相同后才允许 `adb install -r`；签名不同立即停下，不能用卸载绕过。

真机至少检查：重复进出文件夹与搜索点歌、打开/收起播放页、Mini Player、收藏、歌单、后台与锁屏。备份恢复先用独立测试数据验证，不覆盖唯一真实数据。

## 2. 补齐公开素材来源

你已确认素材可公开分发。请保留能说明来源和许可范围的凭据，按 [第三方声明](../THIRD_PARTY_NOTICES.md) 清单填入可公开信息；合同或私人身份文件不要进仓库。截图要检查通知栏、目录路径和个人信息。

公开源码前检查当前文件和 Git 历史，不只看 `.gitignore`。它只能阻止以后误提交，不会抹掉已经提交的文件。

禁止发布：音乐文件、个人 LRC、`.db`、`.harmonybackup`、`key.properties`、私钥、密码、`.tooling`、构建缓存和私人日志。没有用户授权不改写旧 Git 历史。

## 3. 先建私有仓库验证

推荐顺序：GitHub 新建空的私有仓库 → 只推经审查的源码和文档 → 跑 Actions → 在另一干净目录克隆并构建 → 复查素材和隐私 → 再由你确认改公开。创建、推送和切公开都是外部操作，需要明确确认后执行。

本地已经有 Git 历史。交付提交应逐文件核对，别用“整个目录上传”把电脑缓存放进去。若决定用干净的新公开历史，应保留原仓库并另行建立发布副本，不能直接抹掉原历史。

GitHub 设置建议：开启双重验证、Private vulnerability reporting、分支保护/合并前检查；公开仓库开启可用的 Secret scanning。CI 不授予写权限，不接触私钥，不自动发布 APK。

## 4. 正式 APK 的签名

专属发布私钥是未来覆盖更新的身份凭证。推荐由你在本机生成，使用密码管理器保存密码，在两个独立、受保护的位置备份私钥。私钥和密码永远不进源码或聊天。

生成命令（交互输入密码，不把密码写进命令历史；路径只是示例，请选择自己的安全目录）：

```sh
keytool -genkeypair -v -keystore /secure/location/blackdog-release.jks -keyalg RSA -keysize 3072 -validity 10000 -alias blackdog
```

在被 Git 忽略的 `android/key.properties` 写本机配置，Windows 路径可用 `/`。`storeFile` 为绝对路径或相对 `android/` 的路径：

```properties
storeFile=/secure/location/blackdog-release.jks
storePassword=仅在本机填写
keyAlias=blackdog
keyPassword=仅在本机填写
```

然后 `tool.ps1 build-release`。缺配置时构建会明确失败，不自动退回调试证书。Linux/macOS 使用 `flutter build apk --release --target-platform android-arm64 --split-per-abi`。

当前手机是调试签名。专属签名不能直接覆盖它；必须先验证外部备份可恢复，再单独安排迁移。不在本轮悄悄换包名或卸载。公开后的版本始终沿用同一发布密钥，版本号和 versionCode 单调增加。

### 当前构建号衔接：按架构核对，不把基号当最终编号

2026-11-03 实际核对：较早 0.4.6 ARM64 测试 APK 的 `versionCode` 为 **2011**，当时源码为 `0.4.6+11`。后续走查源码与 Flutter 插件确认：当前 `--split-per-abi` 对 ARM64 使用“基号 + 2000”，所以这一差异本身不是编号回退 Bug。之前把二者差异直接列为阻断的判断已更正。

本轮源码递增为 `0.4.6+12`，修复脚本参数透传；在这套固定工具链中，预期 ARM64 拆分包为 2012。曾以基号 2012 试构建，实包变为 4012，已隔离该未分发产物，不当成 2012 交付。后续需分别记录源码基号、ABI 与最终 APK 编号；不要跨“拆分/通用包”直接比较基号。若某设备已经安装更高编号，先停止另行安排，不能强制降级。

版本号提高不能解决签名不一致，两项要分别检查。不使用降级安装、卸载或清数据绕过这两个问题；本次构建号修正没有更换发布密钥。

## 5. 真正发布前的检查单

- 静态检查、Flutter 回归、原生解析、歌词工具测试和 APK 构建通过；跳过项单列。
- 在干净克隆中重现构建，远端 CI 确实绿灯，不把“写了 CI 文件”当“CI 已通过”。
- 备份导出/恢复经过隔离环境完整演练，包括失败回退。
- 真机至少两小时连续播放，检查锁屏、后台、耳机和音频焦点打断；记录实际结果。
- 素材与依赖许可证核对；公开截图不暴露个人数据；漏洞渠道配置正确。
- 正式证书确认、密钥备份完成；测试签名包与正式包清楚区分。
- `pubspec.yaml`、Git 提交/Tag、APK 内版本、校验值、发布说明一一对应。

通过后由你确认发布：标记测试版或预发布版本，不承诺“100%无 Bug”。Release 附 APK、SHA-256、版本说明、已知问题、数据升级/备份提示及 LICENSE/第三方声明。没有补完这些项目之前，只交付测试候选版。
